# 研究文档管理规范

本页是结构层权威正文；整体关系见 [项目结构](../project/GUIDE.md)，本区实例见 [EXAMPLE](EXAMPLE.md)。

当前规范：修订 4（2026-10-21；职责区说明增强，计划布局沿用修订 3）。默认一个仓库对应一个项目，文档入口为 docs/PROJECT.md。已有 doc、外部文档根或多项目工作区按真实映射接入，不为模板迁移。优化 skill 的授权不等于修改作为案例提供的项目。

## 默认结构与增长规则

```text
docs/
├── README.md                  # 本区架构、读写样例与导航
├── PROJECT.md                 # 项目目标、边界、权威路径、计划入口
└── plans/
    └── {plan_id}/
        ├── PLAN.md            # 目标、本计划资源与目录、方案、整体验收
        ├── TASK.md            # 本计划任务清单、当前状态、证据、下一步
        ├── LOG.md             # 按时间追加的重要执行事件
        ├── FINDINGS.md        # 按研究问题整理发现与解释；按需
        ├── references/        # 计划专属参考资料；按需
        └── decisions/         # 重要决定及理由；按需
```

文档树默认创建 README、PROJECT 和活跃计划的 PLAN、TASK、LOG；仓根另有 AGENTS、README、.gitignore，见 [入口规范](../project/entrypoints.md)。其余有内容才创建；不默认创建 PROGRESS、多层 INDEX、项目 LOG、releases、audits 或每任务一个目录。生成模板不代表分析已运行或验收通过。

- TASK 难以支持多人独立维护时，拆为 tasks/T01-name.md；TASK.md 留入口，状态仅在拆出的文件维护，PLAN.task_files 指向实际任务文件。
- FINDINGS 包含多个独立问题时拆成 findings/{question_id}.md；FINDINGS.md 留索引，不复制指标。
- LOG 太长时按年份拆分，保留原入口和可解析链接。
- 确有跨计划长期共用资料时才建 docs/shared/；一个原件，各计划引用。共用操作步骤成熟后再整理 SOP。
- 正式交付需要固定采用版本时增加计划内 DELIVERY.md，记录采用 run、代码版本、图表和材料清单；多次交付确有需要再拆目录。
- 详细检查报告可在计划内独立成文，由 TASK 链接；简短检查结果直接写任务验收区。
- 完成的计划保留原路径并更新状态，不为归档搬目录或断开链接。

## 本计划资源与目录

PLAN 是一项研究工作的整合入口。目标之后、详细方法之前固定设置“本计划资源与目录”，让人和新 AI 会话只读本计划就能定位数据、实现、结果与依据。现有“四个目录”“目录总表”满足要求时直接沿用或改为统一标题，不另建 PATHS、RESOURCES 或 INDEX。

四类资源均须有明确说明；每类可有多行，区分目录和关键文件。使用 [PLAN 模板](../../modules/plan/assets/PLAN.md)，列完整绝对路径或资源 URI、用途与范围、读写边界、核对状态／日期。路径未知写待核对；不适用写理由；拟建路径不能标成已经存在。禁止用省略号、相对路径或“在 PROJECT 里”代替本计划的具体入口。跨机器写主机身份＋该机绝对路径，不能把本机映射当作远端事实。

| 类别 | 至少应让读者知道什么 |
|---|---|
| 数据 | 原始输入实际位置、最终纳入批次／范围、选样依据或清单入口、共享派生版本；明确只读和受控材料，新增数据不自动纳入当前分析 |
| 代码 | 本计划可修改的实现目录与主要入口、配置与环境说明；外部参考实现单独标只读，不把库源码路径当成本计划代码落点 |
| 结果 | 实际结果根、台账及运行命名约定；已用基准／关键 run 和产物的完整位置。既有结果跨多个根时逐一列明，不强行合并；尚未运行则明确注明 |
| 参考资料 | 文献／综述、参考源码、实验程序存档、历史方案／决定等实际入口；每项说明依据用途与版本／章节，已有外部资料不为目录整齐再复制一份 |

资源表之后简述数据范围和输入→实现／配置→产物→解释／下游的关系。不能只列四个大目录而不说明本计划真正使用哪些材料。敏感个体名单、临床内容和凭据不进入资源表；只引用受控位置与访问边界。路径核对只检查必要目录／元数据，不为列路径读入个体原始记录。

PROJECT 维护全项目共享资源身份与根映射；PLAN 维护本计划选择了哪些资源、用于什么和从哪里进入。这是有明确用途的导航摘要，不是第二套数据或运行台账：完整版本清单在数据记录，完整运行清单在 registry，具体来源在 run。PLAN 的路径摘要引用权威入口；共享根变化时同步涉及计划的摘要，不能让两处独立漂移。

TASK 和接续记录引用此节，FINDINGS 引用具体证据，LOG 记录资源选择的重要变更。方法章节只引用资源，不再维护第二张散落目录表。引用旧会话可说明决策来源，但不能把会话 ID 当作数据、代码或结果入口。

写完后做一次“接手检查”：从 PLAN 能否找到四类资源，判断可修改位置、最终输入范围、输出去处及哪些路径尚未核对。check_plans.py 当前不检查该表的完整性、路径可访问性或语义；元数据校验通过不代表这项检查通过。现有项目只读接入时报告缺口，实质修订时在授权范围内补齐。

填写完整的计划资源总表示例见 [文档样例](EXAMPLE.md#本计划资源与目录示例)，不是强制创建更多目录。

## 同一计划的多个历史版本

计划目录只保留一个当前权威 PLAN.md。这里的“最终版本”是当前已选定、供执行的方案，不表示计划已经完成。其他 PLAN_v1、日期版等历史方案放在本计划 backup/，有历史内容才创建；任务、日志和参考资料不因为是旧文件就被一并归档。

整理前核对版本关系、正文差异、任务引用和用户指定版本，不凭最新修改时间推定最终稿；无法判定时保留材料并标待确认，不擅自合并不同研究方案。同一计划的迭代可归档，不同目标的独立计划仍分别维护。

无可靠版本控制时，采用 backup/<日期>-<原文件名>，重名加序号，避免覆盖；修改当前方案前按需要保存快照。使用 [历史索引模板](../../assets/templates/plan-backup-index.md) 记录来源、版本、日期、替代原因及当前入口。历史文件只供追溯，校验器不能把 backup 内 PLAN 当作活跃计划或把历史任务当成当前状态。

有 jj／Git 时可以用已实际保存的提交追溯历史，记录仓库、提交标识、文件路径与取回方法；未提交文件不能视为已备份。仓库不可用或文件未纳入版本控制时，文件夹备份即可，不强制初始化仓库。可以同时保留版本历史和必要历史材料，但不复制出多个当前方案。jj 仓库遵守既有 VCS 约定，不改用 Git 提交。

搬移、归档和清理均限定在当前授权范围；更新当前入口与受影响引用，保留历史内容，不以“只留最终版”为由直接删除旧文件。backup 不是数据备份，也不替代需要的独立介质副本。

## 唯一事实源

| 文件 | 内容与维护方式 |
|---|---|
| PROJECT | 当前项目目标、边界、责任、方向词表、代码／数据／环境绝对路径、共享产品与消费者、访问与保存约定；内含计划入口；当前重点只链接相关 TASK 接续区，不复制具体下一动作或任务状态 |
| PLAN | 当前研究问题、本计划资源与目录、探索／确认性质、方案修订、比较条件、里程碑、停止条件和整体验收；任务只引用，不再维护任务进度或接续副本 |
| TASK | 每个任务的身份、负责人、状态、依赖、验收、证据、阻塞与下一动作；是任务当前状态唯一来源 |
| LOG | 日期、任务／run、关键动作、结果或异常、恢复与证据链接；追加更正，不覆盖历史，不复制终端完整输出 |
| FINDINGS | 按问题组织实际观察、解释、限制、全部尝试的入口及证据版本；预期写 PLAN，实际结果写这里 |
| decisions | 当时的问题、约束、备选、选择及理由；重要变化新建记录并关联被替代项 |
| references | 外部依据、既有材料和阅读笔记；说明来源、版本、用途和链接，不把参考材料当成已采纳方案 |

方向只是标签，与计划多对多，不增加物理父目录。run 不是 task；一任务可多次运行，多计划可引用同一 run。数据、图表、模型、机器日志留在实际运行目录，文档引用 run_id、配置／代码版本和产物路径，不复制成第二份事实源。论文由 Zotero 管理时引用条目、DOI 和阅读笔记，无须再建 PDF 库。需要固定参考版本时说明版本与来源。

## 任务记录与校验

新 PLAN 头部使用 project_id、plan_id、directions、status、owner、updated、depends_on、evidence、checks_passed 和 task_files: [TASK.md]。默认 TASK 的 YAML 头含 plan_id、owner、updated、tasks 列表；每项保存 task_id、status、done_when、depends_on、evidence、reason、resume_when 及必要的 owner、updated 覆盖。正文按 task_id 写步骤、验收说明和接续，状态只在头部维护。

状态沿用：未开始、已承诺、进行中、待判断、受阻、待复核、暂缓、完成、取消。完成有证据；受阻／取消有原因；暂缓有恢复条件。计划完成还需整体解释与检查，不能只看任务打勾。科学阴性可完成；采用、运行失败、决定状态与任务状态分开。

任务依赖在项目内用 plan_id#task_id，计划依赖用 plan_id。跨项目完整身份为 project_id/plan_id#task_id，当前校验器不自动解析跨项目依赖，须人工核对并如实说明边界。证据相对路径相对 --root，task_files 相对 PLAN 所在目录；命令参数使用绝对路径。

check_plans.py 支持新 TASK 清单、旧独立 TASK 文件及旧 PLAN 内嵌 tasks；不能同时维护多份任务事实源。脚本检查身份、依赖和证据文件，不判断科学有效性，也不证明模板占位已填写。

## 决定、解释与交付

日常操作写 LOG，不强制 ADR。改变纳排标准、主分析方法、验证划分、关键数据版本或架构边界时才独立记录。使用 MADR 的背景、选项、选择与理由，按需要补状态、日期、代价和落实核对；如 decisions/0001-validation-split.md。研究方法决定注明其性质与证据范围，记录选择不等于科学验证。

跨计划决定由主责计划维护一份，PROJECT 与其他计划引用；不在各计划复制相同决定。已采纳记录保留原理由；可补状态和落实证据，标时间。改变选择时新记录链接旧记录。

交付事件写 LOG；正式固定采用范围用 DELIVERY.md 和既有交付模板。记录版本、采用来源、检查与限制；准备研究包不等于授权发布。原始数据只读、安全四口、备份、终评准入仍遵守日常规范，不因目录精简降低研究要求。

## 日常更新与扩展

进入：PROJECT → 相关 PLAN → TASK 当前状态与 LOG 最近事件；按问题读 FINDINGS、决定和参考资料，避免加载整个资料库。TASK 接续区记录当前研究问题、阶段、已知、在跑、卡点、待解释、下一步与核对边界；机器、作业号、余量与核对时间按需要引用运行记录。切换焦点不停止后台作业。

执行：保存运行事实与产物 → 更新 TASK 状态及证据 → 在 LOG 追加关键事件 → 按问题更新 FINDINGS → 重要选择写决定 → 仅在范围或方案变化时更新 PLAN；PROJECT 的计划入口、当前重点链接或共享约定变化时才更新。

收尾轻检本次涉及的任务、引用、结果与接续。重大结构变化、共享依赖变化或正式采用前检查受影响范围；其他检查周期由项目需要确定，不默认七天审计。检查注明通过／失败／未检查与证据，结果写 TASK 或链接报告，不强制 audits 目录。

写前重读、同文件单写入者、发现并发变化先合并。多文件更新不是原子事务，失败时记录最后完成步骤和待同步项。共享产物变化核对消费者。不能覆盖人工解释、只保留最好结果、混用版本或把脚本通过当科学有效。

## 兼容与授权

旧项目先登记入口映射，不自动迁移、拆分历史 LOG、重排参考资料或重建状态源。迁移须在用户授权范围内：保留来源和恢复路径，核对身份、条目、依赖、证据及链接后切换。修改 skill、讨论方案与应用到具体项目是不同操作范围。

旧版 progress、index、release、audit、独立 task 模板继续保留作兼容或扩展资源，不作为默认必建清单。新对象 ID 用小写 ASCII 字母／数字和连字符，避开 Windows 保留名；日期用 ISO 8601，时间注明时区；旧标识不静默改名。

## 依据与模板

- The Turing Way：[Research Compendia](https://book.the-turing-way.org/reproducible-research/compendia/)：可理解、可复现，区分数据／方法／产物与计算环境。
- awesome-architecture 的“共享上下文架构”与“架构决策记录与演进”：明确事实源，记录取舍；信息职责不等于必须新建目录。
- [MADR](https://adr.github.io/madr/)：使用最小决定记录，按需要扩展。

本页是上述原则结合用户工作方式的设计，不是三份资料共同规定的目录标准。

模板见 [PROJECT](../../assets/templates/project-contract.md)、[PLAN](../../modules/plan/assets/PLAN.md)、[TASK](../../modules/plan/assets/TASK.md)、[LOG](../../assets/templates/work-log.md)、[发现](../../assets/templates/analysis.md)、[决定](../../assets/templates/architecture-decision.md)、[交付](../../assets/templates/release.md)。生成器用法见 [模板指南](../../docs/template-guide.md)。

涉及新目录、历史归档与迁移时，以 [文件归属规则](../project/placement-rules.md) 核对位置和授权；整理计划须明确现状、目标、唯一归属、引用及验证。

## 项目内入口、内部模块与样例

采用本规范的新建文档区使用 docs/README.md 说明真实文档树、各文件职责、阅读顺序与一个计划更新样例；旧项目已有等价入口则复用。PROJECT 仍负责目标和资源映射，TASK 仍是任务状态源。计划自身由 PLAN/TASK/LOG 说明架构、接口与接续，不强制每个计划再建 README。

新增文档先依职责定位；结构或导航变化时同轮同步文档入口。完整填写示例见 [EXAMPLE](EXAMPLE.md)，根区说明可用 [区 README 模板](../../assets/templates/area-readme.md)。
